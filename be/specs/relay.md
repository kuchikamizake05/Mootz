# Meet relay recovery

The worker is opt-in; it never requires a funded account for local fixtures. Public canonical ABI is injected into createViemMeetTransport. The CLI owner supplies a dedicated server-only relayer key, selected registry and chain 10143 only after deployment verification. No participant or Privy key is reused.

processMeetOutbox(pool, transport, options) bounds batches to 1–100 and leases to 1–600 seconds. A PostgreSQL session advisory lock covers the whole invocation. A single database must coordinate every process using this relayer account: do not share the key across deployments or send unrelated transactions from it. Pending signed outbox rows block preparing fresh transactions even when their retry backoff is active. A retry resends precisely the persisted signed bytes/hash, never signs a replacement with a potentially reused nonce. Before any broadcast the raw bytes and keccak hash are durably stored together. A crash after broadcast is reconciled from the same payload. The worker never changes or deletes Dots.

Matching readback requires both participants, accepted server second, event ID and commitment. An explicit recorded flag must be true; zero-valued absent records and RPC failures never establish success. A receipt alone is insufficient. Both signed RECORD_MEET actions, domain-aware signatures, distinct wallets, signed Offer digest, UUID and 60-second lifetime are checked defensively. The viem transport checks chain, registry code, RELAYER_ROLE and absence of participant account code/delegation before signing.

Unsigned records beyond acceptedAt + 300 seconds become not_saved only after a successful chain absence read. RPC failure retains pending with bounded exponential backoff (2–30 seconds), generic DEPENDENCY_RETRY only; no provider errors, RPC URLs or keys are recorded. A signed transaction with unresolved receipt retains its outbox entry and blocks fresh nonces even after the deadline; it is no longer broadcast after the deadline. This may intentionally stall the worker until the transaction is mined/reverted or an operator resolves the nonce. Never clear this row merely to resume throughput. A known revert is terminal and does not remove the valid Dot. Gas replacement/cancellation and automatic nonce recovery remain unimplemented. Separate read-only finality monitoring and operator diagnosis are described below.

Local tests use synthetic signed payloads and a real PostgreSQL transaction store with injected RPC outcomes. They cover ambiguous broadcast, exact-byte retry, readback mismatch, opt-out, expiry vs RPC outage, success/revert, session locking, and a second job blocked behind unresolved signed nonce. Transport fixtures check canonical ABI encoding, deployment/role/account-code prerequisites and missing-receipt vs provider errors. No live chain transaction is sent by these tests.

Saved Meet transactions are also validated before consulting any receipt/readback or releasing the reserved nonce. Cryptographic sender recovery must match the configured dedicated relayer; type must be EIP-1559, chain10143, exact configured registry, zero value and exact recordMeet calldata including both signatures/acceptedAt. The transaction hash must match the raw bytes. Gas is bounded at2,000,000. `MEET_RELAY_MAX_FEE_GWEI` defaults to500 and `MEET_RELAY_MAX_PRIORITY_FEE_GWEI` to50, with hard maxima1000/100 whole gwei; priority fee cannot exceed max fee. Prepared requests and newly signed output receive the same checks before persistence/broadcast. Actual gas and fees come from viem preparation, not the policy ceilings. Lower budgets only after signed queues drain, as saved bytes must pass the same policy. Never clear a pending transaction to bypass a lower budget.

The separate [read-only chain worker](chain-sync.md) reconciles canonical receipts and finality without changing submission jobs or Dots. Dot responses expose this evidence separately from provisional recorded status. [Nonce inspection](nonce-recovery.md) provides bounded operator diagnosis; automatic replacement/cancellation remains outside this implementation.

Invalid or incomplete saved bytes/hash stay pending, even if an unrelated receipt or record appears successful. Drain pending transactions before relayer key rotation: a saved transaction signed by another key cannot be safely resumed by the new configuration. Do not erase pending jobs to bypass this guard. Both updated workers must share the same database and lock protocol, including the crossqueue unresolved-transaction guard.
