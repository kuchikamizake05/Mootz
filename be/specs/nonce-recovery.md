# Relayer nonce inspection and recovery

`npm run relay:inspect` is a bounded, read-only snapshot of the Meet and Event claim outboxes plus the dedicated relayer account. It reads the configured RPC and database, and does not lease jobs, alter rows, broadcast transactions, or sign anything. The command requires the private server configuration used by the relayer; output omits the key, raw signed bytes, signatures, RPC URL, and provider error details. The relayer key is used only to derive the account address for public account reads.

The report includes queue/job ID, age, retry count, a known/sanitized last-error category, signed transaction nonce/hash, receipt state, whether a finalized account nonce has passed the saved nonce, job expiry, and account latest/pending/finalized nonce and balance. It inspects at most 100 active jobs across the two queues. A truncated snapshot is not evidence that no other unresolved job exists. `finalizedNonce` may be unavailable if the RPC provider does not support the `finalized` tag. A nonce lower than that finalized count means the nonce is consumed, but does not identify the transaction that consumed it. This can indicate an external sender or a replacement; investigate chain history using approved operator tooling before drawing a conclusion.

## Operator procedure

1. Run `npm run relay:inspect` from `be/` in the configured private server environment. Do not paste its output into public tickets if job IDs or transaction hashes are sensitive in the operating context.
2. Check the queue and relayer snapshot. The PostgreSQL session advisory lock `729610143` coordinates both workers and prevents either from allocating a fresh nonce while an unresolved signed job exists. Keep both workers on the same database and use only the dedicated relayer account for these queues.
3. If the transaction is pending, unexpired, its finalized account nonce has not passed the saved nonce, and sender/hash checks match, allow the worker to retry the exact persisted bytes after its regular signed-payload, chain, destination, calldata, and hash validation. A retry must use the original bytes. Do not prepare a new transaction for that nonce.
4. A successful receipt still needs the worker's application readback. For Meet, that is the exact recorded Meet record; for claims it is the expected receipt event plus ownership and issuer-nonce readback. A revert can be completed by the worker only after its existing checks. This inspection command itself never marks a job complete.
5. If the job is expired, leave its saved bytes and nonce reservation in place. Expiry prevents creating a new signed operation; it does not prove that the original transaction cannot land. Continue receipt/readback inspection and escalate unresolved outcomes.
6. If the finalized account nonce passed the job nonce but its stored hash has no known receipt, find the transaction that consumed the nonce and confirm its sender, nonce, destination, and outcome. The database lock cannot coordinate wallets, deployments, or services that send outside this shared database.
7. If diagnosis establishes that an explicit replacement or cancellation transaction is necessary, prepare a separate change plan with the exact account, nonce, chain, fees, and intended effect. Obtain separate explicit authorization before signing or broadcasting it. Preserve the original outbox row until its outcome and the application-level state are reconciled. Never delete a pending row, clear signed fields, reset account nonce state, rotate the relayer key to bypass the job, or manually mark success.
8. Review native balance and fund the relayer through the approved funding process if needed. The inspection command does not initiate funding. Confirm the configured deployment and role state using the existing deployment runbooks before re-enabling a worker after a configuration issue.

The snapshot provides evidence to guide a human; it is not a recovery executor, transaction-finality policy, or reorg monitor. Current queue completion remains provisional under the existing worker rules. Replacement/cancellation requires separate implementation and transaction authorization. Completed-receipt reconciliation and finalized-state observations are supplied by the separate read-only chain-sync worker; see [chain sync](chain-sync.md).
