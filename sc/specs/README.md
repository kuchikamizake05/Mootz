# Candidate signing protocol v1 — INT-01 review required

**Not a frozen FE/BE agreement.** Refs INT-01, SC-01, SC-02. Contracts and public synthetic fixtures implement this candidate only. The backend adapter is described in docs/int-01-baseline.md; live deployment and client acceptance require separate verification.

Canonical machine-readable definitions/helpers: [typed-data.mjs](typed-data.mjs). Reproducible public vectors: [vectors.json](vectors.json), generated by `npm run vectors` in `sc/`. Foundry `VectorsTest` compares their digests against contract hash functions. ABI is generated in [../abi](../abi/). Never copy/edit field ordering or ABI by hand.

## Domain and encoding

| Message | EIP-712 name | version | primaryType |
| --- | --- | --- | --- |
| Offer/Accept | MootzMeetRegistry | 1 | MeetOffer / MeetAccept |
| Event claim | MootzEventCollection | 1 | Claim |

Domains always include actual `chainId` and actual `verifyingContract`. Fixture domains in vectors are synthetic, NOT deployed addresses. Target testnet chain ID is 10143; a chain ID alone does not distinguish our local Anvil fixture from Monad, so always verify RPC/network and bytecode too. Integers use seconds/uint256 (JSON vectors use safely representable numbers; use bigint for viem).

`action` is bytes32 `keccak256(UTF8("RECORD_MEET"))` or `keccak256(UTF8("OFFCHAIN_MEET"))`. No personal-sign wrapper. Require 65-byte canonical low-s ECDSA signatures. This candidate supports undelegated EOA signers only, not ERC-1271/passkey/delegated EIP-7702 wallets; this is not a claim that two wallets mean two people. ERC1155 recipients may be contracts implementing the receiver hook, but voucher issuers must be EOAs.

Offer fields, in exact order: `action bytes32, meetId bytes32, momentId bytes32, photoCommitment bytes32, poster address, nonce bytes32, issuedAt uint256, expiresAt uint256, eventId bytes32`.

Accept: `action bytes32, offerDigest bytes32, scanner address`. `offerDigest` is the complete EIP-712 Offer digest, including domain. Accept is bound to that exact Offer and scanner; it needs no independent nonce because the Offer's unique ID and poster nonce are consumed atomically. A newly opened QR needs a new cryptographically random nonce and Meet ID. Nonces are scoped to poster and cannot be reused across events/IDs. `meetId`, `momentId`, commitment must be nonzero; `eventId=0` means no event and does not increment the zero-event bucket. Wallet counts are incremented for both participants.

For UUID-based IDs use the 16 raw UUID bytes right-padded with 16 zero bytes (`uuidBytes32` helper), without byte-order reversal or string hashing. `eventMeetCount(wallet,eventId)` requires that exact bytes32 encoding. Fixture vectors cover this conversion. Collection IDs are separate positive uint256 identifiers, mapped by `collections(id).eventId`.

Candidate photo commitment: `keccak256(abi.encode(uint256(1), bytes32(momentId), bytes32(frontSHA256), bytes32(backSHA256), bytes32(salt)))`. Front/back SHA256 digests refer to the exact immutable normalized bytes reviewed by the scanner; order is front then back. Salt must be CSPRNG 32 bytes for real private media. It and source digests remain offchain. Test salts and synthetic text digests are public fixtures and must never be reused for private media. The internal SHA256 pair commitment is separate from the chain commitment. The backend chain adapter derives the specified keccak commitment from immutable media inputs. Contract only binds the commitment; it does not fetch/check media.

## Time and relay trust

`expiresAt = issuedAt + 60`. Backend must RECEIVE and VALIDATE Accept before expiry, reject exactly-at-expiry, verify current account-wallet bindings, both signatures and consent, immutable media/preview, foreground GPS distance <=100m, accuracy/staleness, pair/area/server-day limits and both event check-ins. No event is added/removed after Offer signing. Event scanner lacking check-in is rejected; do not silently strip the event tag.

Only a `RELAYER_ROLE` caller may submit `recordMeet(offer,accept,posterSignature,scannerSignature,acceptedAt)`. That caller attests its backend validated the above at `acceptedAt`. Contract requires `issuedAt <= acceptedAt < expiresAt`, `acceptedAt <= block.timestamp`, QR lifetime exactly 60s and `block.timestamp <= acceptedAt + 300`. The 300s relay window is a **candidate constant needing INT-01 approval**, separate from QR expiry. Transaction retries may arrive after QR expiry. The contract cannot prove historical signing time or GPS correctness; a compromised relay can lie about acceptance/eligibility/time inside the bounded window but cannot forge participant EOA signatures or change opt-out into opt-in.

Both actions must be RECORD_MEET, two nonzero distinct undelegated EOAs, matching digest and signatures. Only after all checks do ID, nonce and counts change. Public record/log contains wallets, Meet ID, event ID, attested acceptedAt and commitment; no location, media URI or name. Failures/retries must never remove a backend Dot. `AlreadyRecorded` requires reading the existing record/receipt before treating reconciliation as success; do not count a retry again.

## Claim policy and authority

Claim fields: `collectionId uint256, recipient address, issuer address, nonce bytes32, deadline uint256`. Issuer signs with the collection domain. Any submitter may relay; signed recipient cannot change. Eligibility/check-in is the issuer/backend's responsibility. Contract checks live `ISSUER_ROLE`, canonical EOA signature, recipient, collection existence, deadline (`block.timestamp <= deadline`), issuer-scoped nonce, unclaimed wallet+collection and remaining supply. Each success reserves nonce/claim/supply before the ERC1155 callback and mints exactly one. Reverting callbacks undo all state. Parallel transactions serialize under EVM execution; the last supply slot is not oversold.

Admin creates positive-ID collections with nonzero event ID/cap and public metadata URI exactly once. Demo Workshop A uses cap 50. Caps and metadata are immutable per collection. No admin mint/burn/alternative mint exists; all non-mint transfers, including batch/empty/zero-value and approvals, revert. Meet recording never mints.

`DEFAULT_ADMIN_ROLE` can create collections and grant/revoke admin, relayer and issuer roles. Role rotation immediately invalidates pending relay/issuer authority. There is no proxy/upgrade/pause/revocation or deletion of historical Meet records. Use controlled role addresses; compromise of an admin can authorize dishonest relays/issuers or create new collections, but cannot bypass participant signatures or mutate an existing collection cap. Admins must review public metadata themselves; contracts do not detect private content in a URI.

## Consumer handoff and remaining gate

FE: use canonical helpers and actual deployed domains; inspect both Offer/Accept consent actions. Display recorded/claimed only after a successful receipt and readback. Keep account and wallet identifiers distinct. Never send salt/media/GPS in calldata. RPC failure must not be shown as zero ownership.

BE: implement the validation/atomic reservation/outbox and issuer-voucher issuance in `be/`; do not import private backend code into clients. Claim/retry and Meet retry keep the same IDs/nonces. Stop after the relay deadline and label Not saved onchain while preserving the Dot. Check contract roles and signing domain at startup.

Organizer: independently authenticate wallet control, then read `balanceOf(wallet,collectionId)` and `eventMeetCount(wallet,eventId)` using the exported ABIs. A nonholder may still have a Meet count; unsaved Meets are absent. These reads do not require the Mootz database.

INT-01 still needs Faaid/Wangsit approval of this candidate, commitment adaptation, relay trust/window, wallet support, ID encoding, actual deployment domains, plus backend-owned accuracy/staleness/grid policy. This document does not lock those team decisions or close dependency #2.
